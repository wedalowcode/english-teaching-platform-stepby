# 第六篇：搭建自动化部署流水线，实现 Git Push 后自动上线

## 一、本篇目标

前面几篇教程，我们已经完成了开发环境、后台基础布局、Git 版本管理，以及腾讯云轻量应用服务器生产环境的搭建。

现在，我们已经具备了应用部署的基础条件。

但是，如果每次修改代码后，都需要手动登录服务器，执行拉取代码、安装依赖、数据库迁移、构建和重启等操作，开发效率仍然不高。

我们希望实现类似 Vercel 的自动部署体验：

**本地代码提交并推送到 GitHub，服务器就自动获取最新代码、执行数据库迁移、构建项目并重启应用。**

本篇将使用 GitHub Actions 实现这套自动化部署流程。

完成后，我们的开发流程将变成：

```text
本地电脑
   │
   │ 修改代码
   │ git add .
   │ git commit
   │ git push
   ▼
GitHub 仓库
   │
   │ 触发 GitHub Actions
   ▼
腾讯云轻量应用服务器
   │
   ├── 获取最新代码
   ├── 安装项目依赖
   ├── Prisma 生成客户端
   ├── 执行数据库迁移
   ├── Next.js 生产环境构建
   ├── 重启应用服务
   │
   ▼
Nginx
   │
   ▼
浏览器访问公网 IP
```

本篇使用的技术：

| 技术 | 作用 |
|---|---|
| GitHub Actions | 监听代码推送，执行自动化任务 |
| SSH | GitHub Actions 安全连接服务器 |
| Git | 服务器获取最新代码 |
| pnpm | 安装项目依赖 |
| Prisma | 生成客户端、执行数据库迁移 |
| Next.js | 构建生产环境应用 |
| systemd | 管理应用进程 |
| Nginx | 将公网请求转发给 Next.js |

## 二、开始之前：理解自动部署的工作原理

### 2.1 什么是 CI/CD？

CI/CD 是软件开发中常见的一套自动化流程。

CI 是 Continuous Integration，持续集成。

简单来说，就是开发人员提交代码后，系统自动执行代码检查、测试和构建，尽早发现问题。

CD 是 Continuous Delivery 或 Continuous Deployment，分别表示持续交付和持续部署。

在本教程中，我们主要实现持续部署：

代码推送到指定分支后，自动将最新版本部署到服务器。

### 2.2 GitHub Actions 是什么？

GitHub Actions 是 GitHub 提供的自动化工作流服务。

我们可以在代码仓库中创建一个工作流文件，告诉 GitHub：

- 什么时候执行任务。
- 在什么环境中执行。
- 需要执行哪些命令。
- 如何连接我们的服务器。

例如，我们可以配置：

```yaml
on:
  push:
    branches:
      - main
```

这段配置表示：

当代码推送到 main 分支时，自动触发工作流。

GitHub Actions 会启动一个临时运行环境，在其中执行我们定义的部署任务。

### 2.3 为什么还需要 SSH？

GitHub Actions 运行在 GitHub 提供的服务器上，而我们的应用运行在腾讯云轻量应用服务器上。

两者是不同的机器。

因此，需要一种安全的远程连接方式，让 GitHub Actions 可以通知腾讯云服务器执行部署。

这里使用 SSH。

SSH 是一种加密的远程登录协议。

我们平时通过下面的命令连接服务器：

```bash
ssh ubuntu@服务器公网IP
```

自动部署时，GitHub Actions 也会使用 SSH 连接服务器，只不过不再通过人工输入密码，而是使用 SSH 密钥完成身份验证。

### 2.4 为什么使用 systemd？

Next.js 项目执行：

```bash
pnpm start
```

就可以启动生产环境服务。

但是，如果我们直接在 SSH 窗口中执行这个命令：

- 关闭终端可能导致应用退出。
- 服务器重启后应用不会自动启动。
- 应用异常退出后不会自动恢复。
- 不方便统一查看运行状态和日志。

Linux 提供了 systemd 服务管理机制。

我们可以将 Next.js 应用注册成一个系统服务，由 systemd 负责启动、停止、重启和监控。

最终由 GitHub Actions 负责触发部署，systemd 负责管理应用进程。

## 三、准备 GitHub 仓库

本教程使用之前创建的项目仓库：

```text
https://github.com/wedalowcode/english-teaching-platform
```

默认以 main 分支作为生产部署分支。

如果你的仓库默认分支不是 main，需要将后续配置中的分支名称统一修改为实际分支。

### 3.1 确认项目 package.json

打开项目根目录的 `package.json`。

当前项目已经定义了：

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  },
  "packageManager": "pnpm@11.9.0"
}
```

这里有几个重要配置：

- `dev`：启动开发环境。
- `build`：构建生产环境应用。
- `start`：启动生产环境应用。
- `packageManager`：声明项目使用的 pnpm 版本。

特别注意，生产环境不能使用 `pnpm dev`，而应该使用：

```bash
pnpm build
pnpm start
```

`pnpm build` 负责生成生产环境构建产物，`pnpm start` 负责启动构建后的应用。

### 3.2 增加数据库迁移命令

当前项目使用 Prisma 7。

在 `package.json` 的 scripts 中增加一个命令：

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint",
    "db:migrate:deploy": "prisma migrate deploy"
  }
}
```

这里增加的是：

```bash
pnpm db:migrate:deploy
```

这个命令用于将尚未应用的数据库迁移执行到生产数据库。

注意：这里只展示需要增加的脚本，不要覆盖原来 package.json 中其他脚本和依赖。

### 3.3 理解 Prisma 迁移

Prisma 提供了数据库迁移机制。

开发阶段，我们通过 Prisma Schema 描述数据库结构，再生成迁移文件。

迁移文件会保存在：

```text
prisma/
└── migrations/
    ├── 迁移目录1/
    │   └── migration.sql
    └── migration_lock.toml
```

这些迁移文件需要提交到 GitHub。

生产环境部署时，执行：

```bash
pnpm db:migrate:deploy
```

Prisma 会读取迁移文件，检查数据库中哪些迁移尚未执行，然后按顺序应用。

这里有一个非常重要的区别：

`prisma migrate dev` 是开发阶段使用的命令，可以创建和应用开发迁移。

`prisma migrate deploy` 是生产环境使用的命令，只应用已经存在的迁移，不会自动根据 Schema 创建新的迁移文件。

因此，**不能在生产服务器上直接使用 `prisma migrate dev`。**

## 四、配置 Prisma 7 数据库连接

当前项目使用 Prisma 7，数据库连接配置与旧版本有所不同。

项目中的 `prisma/schema.prisma` 已经使用：

```prisma
datasource db {
  provider = "postgresql"
}
```

这里没有配置数据库 URL。

Prisma 7 将连接配置放在独立的配置文件中。

### 4.1 创建 prisma.config.ts

在项目根目录创建：

```text
prisma.config.ts
```

完整代码：

```typescript
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: env("DATABASE_URL"),
  },
});
```

代码讲解：

**第一部分：导入配置函数**

```typescript
import { defineConfig, env } from "prisma/config";
```

`defineConfig` 用来定义 Prisma 配置。

`env` 用来读取环境变量。

**第二部分：指定 Schema 文件**

```typescript
schema: "prisma/schema.prisma",
```

告诉 Prisma 数据模型定义文件的位置。

**第三部分：指定迁移目录**

```typescript
migrations: {
  path: "prisma/migrations",
},
```

告诉 Prisma 数据库迁移文件存放在哪里。

**第四部分：指定数据库连接**

```typescript
datasource: {
  url: env("DATABASE_URL"),
},
```

数据库连接地址从环境变量 `DATABASE_URL` 中读取。

这样开发环境和生产环境就可以使用不同的数据库，而不需要修改代码。

注意：项目根目录的 `.env` 可以供本地开发使用，但生产环境的数据库连接地址应该单独保存在服务器上。

## 五、配置生产环境变量

数据库连接密码、认证密钥等信息不能直接写入代码，也不能提交到 GitHub。

我们需要在服务器上保存生产环境变量。

### 5.1 登录腾讯云服务器

使用 SSH 连接：

```bash
ssh ubuntu@你的服务器公网IP
```

创建生产环境配置目录：

```bash
sudo mkdir -p /etc/english-teaching-platform
```

创建环境变量文件：

```bash
sudo nano /etc/english-teaching-platform/production.env
```

写入：

```env
NODE_ENV=production
DATABASE_URL="postgresql://english_app:数据库密码@127.0.0.1:5432/english_teaching"
```

这里需要将数据库密码替换为第五篇中创建的实际密码。

如果数据库密码包含特殊字符，需要按照 PostgreSQL URL 规则进行 URL 编码。

项目还使用 Better Auth。如果当前认证配置需要 `BETTER_AUTH_SECRET`、`BETTER_AUTH_URL` 等环境变量，也必须将它们配置在这个生产环境文件中。

例如：

```env
BETTER_AUTH_SECRET=替换为实际生成的高强度密钥
BETTER_AUTH_URL=http://你的服务器公网IP
```

具体变量名称和要求以项目当前 Better Auth 配置为准，不要随意添加没有被代码读取的变量。

### 5.2 设置环境文件权限

执行：

```bash
sudo chown root:ubuntu /etc/english-teaching-platform/production.env
```

设置权限：

```bash
sudo chmod 640 /etc/english-teaching-platform/production.env
```

这样 root 用户可以管理文件，ubuntu 用户可以读取文件，其他普通用户无法读取。

注意：生产环境变量文件不要放进项目目录，也不要提交到 GitHub。

## 六、配置服务器 SSH 部署入口

接下来需要让 GitHub Actions 可以安全连接腾讯云服务器。

### 6.1 在本地生成部署专用 SSH 密钥

在本地电脑打开 PowerShell。

执行：

```bash
ssh-keygen -t ed25519 -C "github-actions-deploy"
```

根据提示输入密钥保存位置。

建议使用单独的密钥文件，例如：

```text
C:\Users\你的用户名\.ssh\github_actions_deploy
```

为了方便 GitHub Actions 非交互式使用，可以在生成时不设置密钥口令。这个私钥只用于部署，不要与日常 SSH 登录密钥混用。

生成后会得到两个文件：

```text
github_actions_deploy
github_actions_deploy.pub
```

其中：

- 没有 `.pub` 的是私钥。
- 有 `.pub` 的是公钥。

私钥需要保存到 GitHub Secrets。

公钥需要添加到服务器。

### 6.2 将公钥添加到服务器

先查看本地公钥内容：

```powershell
Get-Content "$env:USERPROFILE\.ssh\github_actions_deploy.pub"
```

复制完整内容。

登录腾讯云服务器，执行：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys
```

将刚才复制的公钥粘贴进去，保存退出。

设置权限：

```bash
chmod 600 ~/.ssh/authorized_keys
```

### 6.3 测试 SSH 密钥连接

回到本地 PowerShell：

```powershell
ssh -i "$env:USERPROFILE\.ssh\github_actions_deploy" ubuntu@你的服务器公网IP
```

如果可以直接连接服务器，不需要输入服务器登录密码，说明密钥认证配置成功。

这里不要关闭原有 SSH 登录方式，先确认新密钥连接正常，再考虑进一步收紧 SSH 登录策略。

如果项目仓库是公开仓库，可以直接执行：

## 八、创建自动部署脚本

接下来是整套自动部署流程的核心。

我们不把所有部署命令直接写在 GitHub Actions 文件中，而是在服务器上创建一个独立的部署脚本。

这样做有两个好处：

1. 部署逻辑保存在服务器上，方便维护。
2. GitHub Actions 只负责触发部署，不需要知道每一个部署细节。

### 8.1 创建部署脚本

服务器执行：

```bash
sudo nano /usr/local/bin/deploy-english.sh
```

写入完整代码：

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

APP_DIR="/var/www/english-teaching-platform"
ENV_FILE="/etc/english-teaching-platform/production.env"
SERVICE_NAME="english-teaching"

echo "========== 开始部署 =========="

cd "$APP_DIR"

if [ ! -f "$ENV_FILE" ]; then
  echo "错误：生产环境变量文件不存在"
  exit 1
fi

# 加载生产环境变量
set -a
source "$ENV_FILE"
set +a

# 检查数据库连接变量
if [ -z "${DATABASE_URL:-}" ]; then
  echo "错误：DATABASE_URL 未配置"
  exit 1
fi

echo "1. 获取最新代码"

git fetch origin main
git reset --hard origin/main

echo "2. 安装项目依赖"

corepack prepare pnpm@11.9.0 --activate

pnpm install --frozen-lockfile

echo "3. 生成 Prisma Client"

pnpm exec prisma generate

echo "4. 执行数据库迁移"

pnpm db:migrate:deploy

echo "5. 构建 Next.js 项目"

pnpm build

echo "6. 重启应用服务"

sudo systemctl restart "$SERVICE_NAME"

echo "7. 检查应用服务"

sudo systemctl is-active --quiet "$SERVICE_NAME"

echo "========== 部署成功 =========="
```

### 8.2 逐段理解部署脚本

**第一部分：严格执行模式**

```bash
set -Eeuo pipefail
```

这是 Bash 脚本常见的安全设置。

- `-e`：命令执行失败时退出。
- `-u`：使用未定义变量时退出。
- `-o pipefail`：管道中的命令失败时，不把整个管道当作成功。
- `-E`：让错误处理机制在函数和子 Shell 中更一致地生效。

这样可以避免前面的步骤失败后，脚本仍然继续执行后面的部署操作。

**第二部分：设置项目目录**

```bash
APP_DIR="/var/www/english-teaching-platform"
```

指定项目代码所在的位置。

**第三部分：读取生产环境变量**

```bash
set -a
source "$ENV_FILE"
set +a
```

将生产环境变量加载到当前 Shell 环境中。

这样 Prisma 执行数据库迁移时，就可以读取 `DATABASE_URL`。

**第四部分：获取最新代码**

```bash
git fetch origin main
git reset --hard origin/main
```

`git fetch` 获取远端最新代码。

`git reset --hard` 将服务器当前工作区和分支重置到远端 main 的最新提交。

注意：这个操作会丢弃服务器代码目录中未提交的本地修改。因此，服务器上的业务代码应当由 Git 管理，不要直接在服务器上修改源代码。

**第五部分：安装依赖**

```bash
pnpm install --frozen-lockfile
```

根据 `pnpm-lock.yaml` 安装依赖。

`--frozen-lockfile` 表示锁文件必须与 package.json 匹配，不允许安装时自动修改锁文件。

**第六部分：生成 Prisma Client**

```bash
pnpm exec prisma generate
```

根据 Prisma Schema 生成数据库客户端。

当前项目使用自定义生成目录：

```prisma
generator client {
  provider = "prisma-client"
  output   = "../app/generated/prisma"
}
```

因此，生成的 Prisma Client 会放在项目的 `app/generated/prisma` 目录中。

**第七部分：执行数据库迁移**

```bash
pnpm db:migrate:deploy
```

将 GitHub 中已经提交的迁移文件应用到生产数据库。

**第八部分：构建项目**

```bash
pnpm build
```

执行 Next.js 生产环境构建。

**第九部分：重启服务**

```bash
sudo systemctl restart "$SERVICE_NAME"
```

构建成功后重启 Next.js 应用。

**第十部分：检查服务状态**

```bash
sudo systemctl is-active --quiet "$SERVICE_NAME"
```

检查应用服务是否处于运行状态。

如果服务没有正常启动，脚本会返回失败。

### 8.3 设置脚本执行权限

执行：

```bash
sudo chmod +x /usr/local/bin/deploy-english.sh
```

到这里，服务器已经具备执行自动部署的能力。

不过，我们还需要创建 systemd 服务，让应用能够持续运行。

## 九、配置 systemd 管理 Next.js

### 9.1 创建服务文件

服务器执行：

```bash
sudo nano /etc/systemd/system/english-teaching.service
```

写入：

```ini
[Unit]
Description=English Teaching Platform
After=network.target postgresql.service
Requires=postgresql.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/var/www/english-teaching-platform
EnvironmentFile=/etc/english-teaching-platform/production.env
Environment=HOSTNAME=127.0.0.1
Environment=PORT=3000
ExecStart=/usr/bin/pnpm start
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 9.2 理解服务配置

**Unit 部分**

```ini
[Unit]
Description=English Teaching Platform
After=network.target postgresql.service
Requires=postgresql.service
```

描述服务名称，并要求 PostgreSQL 服务启动后再启动应用。

**Service 部分**

```ini
[Service]
Type=simple
User=ubuntu
WorkingDirectory=/var/www/english-teaching-platform
```

指定：

- 服务类型为 simple。
- 使用 ubuntu 用户运行应用。
- 项目工作目录为 `/var/www/english-teaching-platform`。

这里不使用 root 运行 Next.js。

**环境变量**

```ini
EnvironmentFile=/etc/english-teaching-platform/production.env
Environment=HOSTNAME=127.0.0.1
Environment=PORT=3000
```

加载生产环境变量，并让 Next.js 监听本机的 3000 端口。

**启动命令**

```ini
ExecStart=/usr/bin/pnpm start
```

执行项目 package.json 中定义的 start 命令。

**异常恢复**

```ini
Restart=always
RestartSec=5
```

应用异常退出后，systemd 会尝试重新启动。

### 9.3 授予部署用户重启服务的权限

部署脚本需要执行：

```bash
sudo systemctl restart english-teaching
```

如果每次都要求输入密码，GitHub Actions 就无法自动完成部署。

我们可以通过 sudoers 配置，只允许 ubuntu 用户执行指定的服务管理命令。

执行：

```bash
sudo visudo -f /etc/sudoers.d/english-teaching
```

写入：

```text
ubuntu ALL=(root) NOPASSWD: /usr/bin/systemctl restart english-teaching, /usr/bin/systemctl is-active english-teaching
```

保存退出。

检查配置：

```bash
sudo visudo -cf /etc/sudoers.d/english-teaching
```

如果显示语法检查通过，说明配置正确。

注意：这里仅授权重启和检查指定服务，不要为了省事直接给 ubuntu 用户开放全部 sudo 免密权限。

### 9.4 启用 systemd 服务

执行：

```bash
sudo systemctl daemon-reload
```

重新加载服务配置。

设置开机启动：

```bash
sudo systemctl enable english-teaching
```

检查服务配置是否已经加载：

```bash
sudo systemctl status english-teaching --no-pager
```

## 十、配置 Nginx 反向代理

第五篇已经安装了 Nginx。

现在需要将公网 HTTP 请求转发到 Next.js 的 3000 端口。

### 10.1 创建 Nginx 配置

执行：

```bash
sudo nano /etc/nginx/sites-available/english-teaching
```

写入：

```nginx
server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://127.0.0.1:3000;

        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

### 10.2 启用网站配置

执行：

```bash
sudo ln -s /etc/nginx/sites-available/english-teaching /etc/nginx/sites-enabled/english-teaching
```

如果默认站点仍然启用，可以移除默认站点的链接：

```bash
sudo rm -f /etc/nginx/sites-enabled/default
```

检查配置：

```bash
sudo nginx -t
```

如果提示：

```text
syntax is ok
test is successful
```

说明配置没有语法错误。

重新加载 Nginx：

```bash
sudo systemctl reload nginx
```

现在 Nginx 已经知道如何将请求转发到 Next.js。

### 10.3 为什么不直接开放 3000 端口？

我们配置了：

```ini
Environment=HOSTNAME=127.0.0.1
Environment=PORT=3000
```

Next.js 只监听服务器本机地址。

外部用户访问：

```text
http://服务器公网IP
```

请求首先进入 Nginx，再转发到：

```text
http://127.0.0.1:3000
```

这样，公网只需要开放 80 端口，不需要开放 3000 端口。

## 十一、配置 GitHub Actions

服务器已经准备好了。

现在让 GitHub 在代码推送时自动触发部署。

### 11.1 获取 SSH 私钥

回到本地电脑。

打开之前生成的私钥文件：

```text
github_actions_deploy
```

复制整个文件内容，包括：

```text
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----
```

注意：这是私钥，不能公开，也不能提交到项目仓库。

### 11.2 获取服务器 SSH 主机指纹

为了避免 GitHub Actions 连接到伪造的服务器，需要验证 SSH 主机身份。

在本地电脑执行：

```bash
ssh-keyscan -H 你的服务器公网IP
```

将输出结果复制保存。

这一步最好通过可信网络获取，并与服务器实际 SSH 主机指纹进行核对，不要把未经验证的扫描结果当成绝对可信的身份凭证。

### 11.3 配置 GitHub Secrets

打开 GitHub 项目仓库：

```text
Settings
  └── Secrets and variables
        └── Actions
```

点击 New repository secret，创建以下三个变量：

| Secret 名称 | 内容 |
|---|---|
| SERVER_HOST | 腾讯云服务器公网 IP |
| SERVER_USER | ubuntu |
| SERVER_SSH_KEY | 前面生成的 SSH 私钥完整内容 |
| SERVER_KNOWN_HOSTS | 前面验证过的 SSH 主机指纹 |

这里实际需要创建四个 Secret。

GitHub Secrets 用于保存敏感信息。

工作流可以读取这些变量，但不会把它们作为普通代码提交到仓库。

### 11.4 创建工作流文件

回到项目根目录，创建目录：

```text
.github/
└── workflows/
```

在 workflows 目录中创建：

```text
deploy.yml
```

完整代码：

```yaml
name: Deploy English Teaching Platform

on:
  push:
    branches:
      - main

  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: production-deploy
  cancel-in-progress: false

jobs:
  deploy:
    name: Deploy to Tencent Cloud
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup SSH
        shell: bash
        env:
          SERVER_SSH_KEY: ${{ secrets.SERVER_SSH_KEY }}
          SERVER_KNOWN_HOSTS: ${{ secrets.SERVER_KNOWN_HOSTS }}
        run: |
          mkdir -p ~/.ssh
          chmod 700 ~/.ssh

          printf '%s\n' "$SERVER_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key

          printf '%s\n' "$SERVER_KNOWN_HOSTS" > ~/.ssh/known_hosts
          chmod 600 ~/.ssh/known_hosts

      - name: Deploy to server
        env:
          SERVER_HOST: ${{ secrets.SERVER_HOST }}
          SERVER_USER: ${{ secrets.SERVER_USER }}
        run: |
          ssh \
            -i ~/.ssh/deploy_key \
            -o BatchMode=yes \
            -o StrictHostKeyChecking=yes \
            "$SERVER_USER@$SERVER_HOST" \
            "sudo -n /usr/local/bin/deploy-english.sh"
```

### 11.5 逐段理解工作流

**第一部分：工作流名称**

```yaml
name: Deploy English Teaching Platform
```

这是工作流在 GitHub Actions 页面显示的名称。

**第二部分：触发条件**

```yaml
on:
  push:
    branches:
      - main
```

当 main 分支收到新的代码推送时，自动执行部署。

另外：

```yaml
workflow_dispatch:
```

表示允许我们在 GitHub 页面手动触发部署。

**第三部分：并发控制**

```yaml
concurrency:
  group: production-deploy
  cancel-in-progress: false
```

避免多个生产部署任务同时修改服务器上的同一份代码。

这里不取消正在执行的部署，而是避免部署任务并发执行。

**第四部分：运行环境**

```yaml
runs-on: ubuntu-latest
```

表示 GitHub Actions 使用 Ubuntu 运行环境。

**第五部分：配置 SSH**

```yaml
SERVER_SSH_KEY: ${{ secrets.SERVER_SSH_KEY }}
```

读取 GitHub Secrets 中的私钥。

然后写入临时 SSH 密钥文件。

**第六部分：执行远程部署**

```bash
ssh ... "sudo -n /usr/local/bin/deploy-english.sh"
```

通过 SSH 连接服务器，执行服务器上的部署脚本。

这里的 `-n` 表示 sudo 不会等待人工输入密码。

如果权限没有配置正确，部署会直接失败，而不是一直等待。

至此，自动部署工作流已经完成。

## 十四、生产部署需要注意的问题

自动部署虽然方便，但生产环境不能只考虑部署成功，还要考虑部署失败和数据安全。

### 14.1 数据库迁移不能随意修改历史记录

生产环境使用：

```bash
pnpm db:migrate:deploy
```

只执行尚未应用的迁移。

不要修改已经在生产环境执行过的历史迁移文件。

如果需要修改数据库结构，应创建新的迁移。

### 14.2 数据库迁移可能影响旧版本应用

本篇的执行顺序是：

```text
数据库迁移
   │
   ▼
Next.js 构建
   │
   ▼
重启应用
```

这意味着数据库结构可能已经更新，但新版本应用尚未启动。

如果构建失败，旧版本应用可能仍然运行，但数据库结构已经发生变化。

因此，后续设计数据库变更时，应该尽量采用向后兼容的迁移方式。

例如：

1. 先增加新字段，不立即删除旧字段。
2. 先让代码兼容新旧结构。
3. 确认新版本运行稳定后，再考虑删除旧字段。

不要把数据库迁移当作普通代码更新，它可能影响线上数据和旧版本应用。

### 14.3 不要把敏感信息提交到 GitHub

以下信息必须保存在服务器或 GitHub Secrets 中：

- 数据库密码。
- Better Auth 密钥。
- 第三方 API 密钥。
- SSH 私钥。
- 其他生产环境凭据。

尤其不要将服务器的 `production.env` 提交到 GitHub。

### 14.4 部署失败时如何排查？

如果 GitHub Actions 失败，先查看 Actions 日志，定位失败步骤。

如果 SSH 成功，但服务器部署失败，可以查看：

```bash
sudo journalctl -u english-teaching -n 100 --no-pager
```

查看应用日志。

查看 Nginx 日志：

```bash
sudo tail -n 100 /var/log/nginx/error.log
```

查看服务状态：

```bash
sudo systemctl status english-teaching --no-pager
```

查看服务器磁盘空间：

```bash
df -h
```

查看内存：

```bash
free -h
```

如果构建失败，不要简单地反复重启服务。先找到构建失败原因，修复代码后再重新推送。

### 14.5 生产环境还需要定期备份

数据库是业务数据的核心。

自动部署不会自动备份数据库。

后续我们还需要配置 PostgreSQL 定时备份，并将备份文件保存到服务器之外的可靠存储位置。

过去：

```text
修改代码
  ↓

  ↓

  ↓
```

现在：

```text
修改代码
  ↓
git push
  ↓
自动部署
  ↓
访问最新版本
```

我们已经拥有了一套轻量级的自动化部署平台。

它没有 Vercel 那样完整的控制台、预览环境和多区域部署能力，但对于当前的个人项目和教学实战来说，已经具备了核心的自动部署能力。
