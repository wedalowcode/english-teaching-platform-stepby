# 英语教学平台08：实现用户新增功能——从表单到数据库

## 一、本篇目标

上一节已经完成用户管理列表查询，实现了从 PostgreSQL 数据库读取用户数据，并通过 Next.js 页面展示用户信息。

但是目前用户管理还只有查询功能，无法在系统中创建新用户。

本篇继续完善用户管理，实现用户新增功能。

完成后，用户可以在后台点击「新增用户」，填写用户资料和初始密码，提交后将数据保存到 PostgreSQL 数据库，并自动返回用户列表。

本篇实现的功能包括：

- 新增用户页面。
- 用户资料表单。
- Zod 表单数据校验。
- Server Action 接收表单提交。
- 服务端密码哈希处理。
- Prisma 创建用户及登录凭据。
- 创建成功后返回用户列表。

最终形成完整的数据处理流程：

```text
用户填写表单
    ↓
React 表单提交
    ↓
Server Action 接收数据
    ↓
Zod 校验数据
    ↓
Service 处理业务逻辑
    ↓
Argon2 生成密码哈希
    ↓
Prisma 写入数据库
    ↓
刷新用户列表
    ↓
返回用户管理页面
```

本篇以 `english-teaching-platform` 完整项目中的用户新增实现为参考，同时遵循 `english-teaching-platform-stepby` 当前的代码结构。

## 二、动手之前：需要掌握哪些知识？

在写代码之前，先理解本篇涉及的几个概念。

### 1. 什么是表单提交？

HTML 表单是浏览器收集用户输入信息的一种方式。

例如：

```html
<form>
  <input name="name" />
  <input name="email" />
  <button type="submit">提交</button>
</form>
```

其中：

- `form` 表示表单。
- `input` 表示输入框。
- `name` 用于标识表单字段。
- `button type="submit"` 表示提交表单。

用户填写姓名和邮箱后，点击提交，浏览器就会将这些字段组织成表单数据。

这里需要特别注意 `name` 属性。

例如：

```tsx
<Input name="name" />
<Input name="email" />
```

提交后，服务端就可以通过字段名称获取对应的值：

```ts
formData.get("name");
formData.get("email");
```

如果没有设置 `name`，这个输入框的数据就不会以对应字段的形式提交。

### 2. 什么是 FormData？

`FormData` 是浏览器和 Web 平台提供的表单数据对象。

Server Action 可以直接接收 `FormData`：

```ts
export async function createUserAction(
  formData: FormData
) {
  const name = formData.get("name");
}
```

其中：

- `get()` 根据字段名称获取一个值。
- `getAll()` 获取同名字段的所有值。
- `entries()` 获取所有字段及其对应的值。

例如：

```ts
const name = String(formData.get("name") ?? "");
```

这段代码表示：

1. 从表单中获取 `name` 字段。
2. 如果字段不存在，就使用空字符串。
3. 将结果转换为字符串。

为什么要转换？

因为 `FormData.get()` 返回的类型可能是字符串，也可能是文件对象，还可能是 `null`。而我们的姓名字段只接受字符串。

### 3. 什么是 Server Action？

Server Action 是 Next.js 提供的一种服务端函数机制。

以前开发前后端分离项目时，通常需要：

```text
前端页面
  ↓ HTTP 请求
后端 API
  ↓
业务逻辑
  ↓
数据库
```

Next.js Server Action 可以简化这个过程。

例如：

```ts
"use server";

export async function createUserAction(
  formData: FormData
) {
  // 在服务端执行
}
```

文件顶部的 `"use server"` 表示该模块中的导出函数可以作为 Server Action 使用。

在客户端组件中，可以将它绑定到表单：

```tsx
<form action={createUserAction}>
  ...
</form>
```

用户提交表单时，Next.js 会负责将数据发送到服务端并执行这个函数。

注意：Server Action 并不意味着可以省略服务端安全校验。它仍然是一个可以被外部请求调用的服务端入口，必须在服务端进行数据校验和权限检查。

### 4. 什么是 useActionState？

React 19 提供了 `useActionState`，可以将 Server Action 和组件状态联系起来。

基本写法：

```tsx
const [state, action, pending] = useActionState(
  serverAction,
  initialState
);
```

三个返回值分别表示：

| 返回值 | 含义 |
|---|---|
| state | Server Action 返回的状态数据 |
| action | 绑定到表单的提交函数 |
| pending | 当前是否正在提交 |

例如：

```tsx
<form action={action}>
  <button type="submit" disabled={pending}>
    {pending ? "正在提交..." : "提交"}
  </button>
</form>
```

这样就能在提交过程中禁用按钮，避免用户重复提交。

如果服务端校验失败，还可以将错误信息返回给组件，在对应的输入框下面显示。

### 5. 为什么密码不能直接保存？

用户注册或新增账号时，不能把明文密码直接写入数据库。

例如：

```text
用户名：zhangsan
密码：12345678
```

如果数据库直接保存 `12345678`，一旦数据库泄露，用户密码就会暴露。

正确做法是使用密码哈希算法，将明文密码转换为不可直接还原的哈希值。

本篇使用 Argon2id。

例如：

```ts
import { hash } from "argon2";

const passwordHash = await hash(password);
```

数据库保存的是 `passwordHash`，而不是原始密码。

后续用户登录时，再通过 Argon2 验证用户输入的密码是否匹配。

### 6. 为什么要区分 Schema、Action 和 Service？

本篇会继续使用前面建立的业务模块结构：

```text
features/users/
├── components/
│   ├── user-list.tsx
│   └── user-create-form.tsx
├── actions.ts
├── schemas.ts
└── service.ts
```

各文件职责如下：

| 文件 | 职责 |
|---|---|
| schemas.ts | 定义数据结构和校验规则 |
| actions.ts | 接收表单提交，组织服务端操作 |
| service.ts | 实现用户创建等业务逻辑 |
| user-create-form.tsx | 展示表单、处理提交状态和错误 |
| user-list.tsx | 展示用户列表及新增入口 |

这样做的好处是页面、数据校验和数据库操作相互分离。

以后新增用户编辑、删除、停用等功能，也可以沿用这个结构。

## 三、第一步：补充用户登录凭据的数据模型

先看一下目前的 `prisma/schema.prisma`。

当前 User 模型只有用户基本资料：

```prisma
model User {
  id            String     @id @default(uuid(7))
  name          String
  email         String     @unique
  emailVerified Boolean    @default(false)
  image         String?

  username      String?    @unique
  phone         String?
  status        UserStatus @default(ACTIVE)

  createdAt     DateTime   @default(now())
  updatedAt     DateTime   @updatedAt

  @@index([createdAt])
}
```

这里有一个问题：

用户基本资料和用户登录凭据不是一回事。

User 记录保存姓名、邮箱、手机号等信息，而 Account 记录负责保存用户的登录账号及密码哈希。

完整项目采用的也是这种结构。

### 1. 修改 User 模型

在 User 模型中增加一条关联：

```prisma
accounts Account[]
```

修改后的完整 User 模型：

```prisma
model User {
  id            String     @id @default(uuid(7))
  name          String
  email         String     @unique
  emailVerified Boolean    @default(false)
  image         String?

  username      String?    @unique
  phone         String?
  status        UserStatus @default(ACTIVE)

  createdAt     DateTime   @default(now())
  updatedAt     DateTime   @updatedAt

  accounts Account[]

  @@index([createdAt])
}
```

`accounts Account[]` 表示一个用户可以关联多条账号记录。

例如，一个用户未来可以拥有不同的登录方式。

### 2. 新增 Account 模型

在 `schema.prisma` 文件中，User 模型下面新增：

```prisma
model Account {
  id         String @id
  accountId  String
  providerId String

  userId String
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  accessToken  String?
  refreshToken String?
  idToken      String?

  accessTokenExpiresAt  DateTime?
  refreshTokenExpiresAt DateTime?

  scope    String?
  password String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([userId])
}
```

解释几个关键字段：

| 字段 | 含义 |
|---|---|
| id | Account 记录的主键 |
| accountId | 登录提供方中的账号标识 |
| providerId | 登录方式，例如 credential |
| userId | 关联的 User ID |
| password | 密码哈希值 |

这里的 `providerId` 使用 `credential`，表示账号密码登录。

这个 Account 结构参考了完整项目的 Better Auth 数据模型，为后续接入 Better Auth 保留兼容基础。

### 3. 安装依赖

stepby 项目目前还没有安装 Argon2 和 server-only。

在项目根目录执行：

```bash
pnpm add argon2 server-only
```

其中：

- `argon2`：负责密码哈希。
- `server-only`：用于标记只能在服务端使用的模块，避免服务端代码被客户端错误引用。

### 4. 执行数据库迁移

修改 Prisma Schema 后，需要将变化同步到 PostgreSQL。

执行：

```bash
pnpm exec prisma migrate dev --name add_account_model --config prisma7.config.ts
```

然后重新生成 Prisma Client：

```bash
pnpm exec prisma generate --config prisma7.config.ts
```

执行成功后，数据库中会新增 Account 表。

**本步骤完成后，数据库具备了保存用户资料和登录凭据的基础结构。**

## 四、第二步：定义用户新增的数据校验规则

接下来修改：

```text
features/users/schemas.ts
```

之前这个文件只定义了用户列表查询条件。

现在还需要增加用户新增的校验规则。

### 1. 完整代码

将文件修改为：

```ts
import { z } from "zod";

export const userListQuerySchema = z.object({
  page: z.coerce.number().int().min(1).catch(1),

  pageSize: z.coerce
    .number()
    .int()
    .refine((value) => [10, 20, 50, 100].includes(value))
    .catch(10),

  keyword: z.string().trim().max(50).catch(""),

  status: z
    .enum(["ACTIVE", "DISABLED"])
    .optional()
    .catch(undefined),
});

// 姓名校验
const nameField = z
  .string()
  .trim()
  .min(1, "请输入姓名")
  .max(50, "姓名不能超过 50 位");

// 邮箱校验
const emailField = z
  .email("邮箱格式不正确")
  .max(100, "邮箱不能超过 100 位")
  .transform((value) => value.toLowerCase());

// 用户名校验
const usernameField = z
  .string()
  .trim()
  .min(3, "用户名至少 3 位")
  .max(30, "用户名不能超过 30 位")
  .regex(
    /^[a-zA-Z0-9_]+$/,
    "只能使用字母、数字和下划线"
  )
  .transform((value) => value.toLowerCase());

// 手机号校验
const phoneField = z
  .string()
  .trim()
  .transform((value) => (value === "" ? null : value))
  .refine(
    (value) => value === null || /^1[3-9]\d{9}$/.test(value),
    "手机号格式不正确"
  );

// 用户新增数据校验
export const createUserSchema = z.object({
  name: nameField,
  email: emailField,
  username: usernameField,
  phone: phoneField,
  password: z
    .string()
    .min(8, "密码至少 8 位")
    .max(128, "密码不能超过 128 位"),
});

// 从 Schema 中推导 TypeScript 类型
export type CreateUserInput = z.infer<
  typeof createUserSchema
>;

// 表单提交状态
export type CreateUserState = {
  message?: string;

  fieldErrors?: Record<string, string[]>;

  values?: {
    name: string;
    email: string;
    username: string;
    phone: string;
  };
};

// 将 Zod 校验错误转换为字段错误
export function toFieldErrors(
  error: z.ZodError
): Record<string, string[]> {
  const flattened = z.flattenError(error).fieldErrors;

  const result: Record<string, string[]> = {};

  for (const [key, messages] of Object.entries(flattened)) {
    if (Array.isArray(messages) && messages.length > 0) {
      result[key] = messages;
    }
  }

  return result;
}
```

### 2. 逐段理解代码

首先看姓名校验：

```ts
const nameField = z
  .string()
  .trim()
  .min(1, "请输入姓名")
  .max(50, "姓名不能超过 50 位");
```

这里使用了 Zod 的链式调用。

- `z.string()`：要求数据必须是字符串。
- `trim()`：去除字符串首尾空格。
- `min(1)`：至少输入一个字符。
- `max(50)`：最多输入 50 个字符。

例如：

```text
" 张三 "
```

经过 `trim()` 后会变成：

```text
"张三"
```

邮箱校验：

```ts
const emailField = z
  .email("邮箱格式不正确")
  .max(100, "邮箱不能超过 100 位")
  .transform((value) => value.toLowerCase());
```

这里的 `transform()` 用于转换数据。

例如：

```text
ZHANGSAN@EXAMPLE.COM
```

最终会统一转换为：

```text
zhangsan@example.com
```

用户名校验：

```ts
.regex(
  /^[a-zA-Z0-9_]+$/,
  "只能使用字母、数字和下划线"
)
```

这里使用正则表达式限制用户名格式。

`^` 表示字符串开始，`$` 表示字符串结束，`+` 表示前面的字符至少出现一次。

因此用户名只能包含英文字母、数字和下划线。

手机号校验：

```ts
const phoneField = z
  .string()
  .trim()
  .transform((value) => (value === "" ? null : value))
  .refine(
    (value) => value === null || /^1[3-9]\d{9}$/.test(value),
    "手机号格式不正确"
  );
```

这里有一个细节：

手机号不是必填项。

如果用户没有填写手机号，就将空字符串转换为 `null`。

如果填写了手机号，则通过正则表达式校验格式。

最后看：

```ts
export const createUserSchema = z.object({
  name: nameField,
  email: emailField,
  username: usernameField,
  phone: phoneField,
  password: z
    .string()
    .min(8, "密码至少 8 位")
    .max(128, "密码不能超过 128 位"),
});
```

`z.object()` 用于定义一个对象结构。

这意味着新增用户必须包含：

- name
- email
- username
- phone
- password

其中手机号可以为空，但其他字段必须满足对应的校验条件。

### 3. 使用 z.infer 推导类型

```ts
export type CreateUserInput = z.infer<
  typeof createUserSchema
>;
```

这里涉及 TypeScript 的两个知识点：

`typeof` 用于获取变量的类型。

`z.infer` 用于从 Zod Schema 中推导出 TypeScript 类型。

这样就不需要再手工重复定义一份数据类型。

尤其要注意，经过 `transform()` 转换后，手机号的最终类型是：

```ts
string | null
```

这也是为什么我们要使用 Zod 推导类型，而不是手工写一份容易不一致的类型。

## 五、第三步：在 Service 中实现用户创建

接下来修改：

```text
features/users/service.ts
```

之前这里已经有 `getUserList()`，负责从数据库查询用户列表。

现在增加 `createUser()`，负责创建用户。

Service 层不负责展示页面，也不负责处理按钮点击，它只负责业务逻辑和数据库操作。

### 1. 完整代码

```ts
import "server-only";

import { hash } from "argon2";

import { Prisma, UserStatus } from "@/lib/generated/prisma/client";
import { db } from "@/lib/db";

import type { CreateUserInput } from "./schemas";

type UserListParams = {
  page: number;
  pageSize: number;
  keyword: string;
  status?: UserStatus;
};

export async function getUserList(params: UserListParams) {
  const { page, pageSize, keyword, status } = params;

  const where: Prisma.UserWhereInput = {};

  if (keyword) {
    where.OR = [
      {
        name: {
          contains: keyword,
          mode: "insensitive",
        },
      },
      {
        username: {
          contains: keyword,
          mode: "insensitive",
        },
      },
      {
        email: {
          contains: keyword,
          mode: "insensitive",
        },
      },
      {
        phone: {
          contains: keyword,
        },
      },
    ];
  }

  if (status) {
    where.status = status;
  }

  const total = await db.user.count({
    where,
  });

  const totalPages = Math.max(
    1,
    Math.ceil(total / pageSize)
  );

  const currentPage = Math.min(
    Math.max(1, page),
    totalPages
  );

  const items = await db.user.findMany({
    where,

    select: {
      id: true,
      name: true,
      email: true,
      username: true,
      phone: true,
      status: true,
      createdAt: true,
    },

    orderBy: [
      { createdAt: "desc" },
      { id: "desc" },
    ],

    skip: (currentPage - 1) * pageSize,
    take: pageSize,
  });

  return {
    items,
    total,
    page: currentPage,
    pageSize,
    totalPages,
  };
}

// 获取 Prisma 错误编码
function getErrorCode(error: unknown): string | undefined {
  if (
    typeof error === "object" &&
    error !== null &&
    "code" in error
  ) {
    const code = (error as { code?: unknown }).code;

    return typeof code === "string" ? code : undefined;
  }

  return undefined;
}

// 获取数据库唯一约束对应的字段
function getUniqueTargetFields(error: unknown): string[] {
  if (
    typeof error !== "object" ||
    error === null ||
    !("meta" in error) ||
    !error.meta ||
    typeof error.meta !== "object" ||
    !("target" in error.meta)
  ) {
    return [];
  }

  const target = error.meta.target;

  if (Array.isArray(target)) {
    return target.map(String);
  }

  return typeof target === "string" ? [target] : [];
}

// 用户创建结果
export type CreateUserResult =
  | {
      success: true;
    }
  | {
      success: false;
      field: "username" | "email";
      message: string;
    };

// 创建用户
export async function createUser(
  input: CreateUserInput
): Promise<CreateUserResult> {
  // 生成用户 ID
  const userId = crypto.randomUUID();

  // 对明文密码进行 Argon2id 哈希处理
  const passwordHash = await hash(input.password);

  try {
    await db.user.create({
      data: {
        id: userId,
        name: input.name,
        email: input.email,
        username: input.username,
        phone: input.phone,

        // 同时创建 credential 登录账号
        accounts: {
          create: {
            id: crypto.randomUUID(),
            accountId: userId,
            providerId: "credential",
            password: passwordHash,
          },
        },
      },

      select: {
        id: true,
      },
    });

    return {
      success: true,
    };
  } catch (error) {
    // P2002 表示数据库唯一约束冲突
    if (getErrorCode(error) === "P2002") {
      const fields = getUniqueTargetFields(error);

      if (fields.includes("username")) {
        return {
          success: false,
          field: "username",
          message: "用户名已存在",
        };
      }

      if (fields.includes("email")) {
        return {
          success: false,
          field: "email",
          message: "邮箱已被使用",
        };
      }
    }

    throw error;
  }
}
```

### 2. 理解 server-only

```ts
import "server-only";
```

这个模块用于明确标记服务端专用代码。

因为 `service.ts` 中会访问数据库，还会处理密码哈希。

这些操作不应该被打包到浏览器端。

使用 `server-only` 可以帮助 Next.js 在错误的导入场景下尽早发现问题。

### 3. 理解密码哈希

```ts
const passwordHash = await hash(input.password);
```

这里调用 Argon2 的 `hash()` 方法。

输入是用户填写的明文密码，返回的是密码哈希值。

数据库只保存哈希值。

注意：密码哈希和普通加密不同。密码哈希不是为了将来解密，而是为了在用户登录时验证密码是否正确。

### 4. 理解 Prisma 关联写入

这是本篇最重要的数据库代码：

```ts
await db.user.create({
  data: {
    id: userId,
    name: input.name,
    email: input.email,
    username: input.username,
    phone: input.phone,

    accounts: {
      create: {
        id: crypto.randomUUID(),
        accountId: userId,
        providerId: "credential",
        password: passwordHash,
      },
    },
  },
});
```

这里不仅创建 User，还通过 `accounts.create` 同时创建 Account。

这属于 Prisma 的嵌套写入。

因为 User 和 Account 已经通过关系字段关联，所以 Prisma 会自动处理两张表之间的关联关系。

从业务角度看，这是一次创建用户的操作。

从数据库角度看，它需要同时写入两条相关记录。

Prisma 的嵌套写入会在同一事务中处理这些关联操作，避免出现用户创建成功、登录凭据却没有创建成功的情况。

### 5. 理解 P2002

```ts
if (getErrorCode(error) === "P2002") {
  const fields = getUniqueTargetFields(error);
}
```

在 Prisma 中，`P2002` 表示唯一约束冲突。

例如：

数据库中已经存在：

```text
username = zhangsan
```

再次创建相同用户名时，数据库会拒绝写入。

我们需要区分究竟是用户名重复，还是邮箱重复。

因此通过错误对象中的 `meta.target` 获取发生冲突的字段。

最后返回：

```ts
{
  success: false,
  field: "username",
  message: "用户名已存在"
}
```

这里没有直接把数据库异常显示给用户，而是将技术异常转换成业务错误信息。

这样前端就可以准确地在用户名输入框下面显示错误。

## 六、第四步：创建 Server Action

现在已经有了数据校验规则，也有了数据库业务逻辑。

接下来需要一个入口，将用户提交的表单数据交给 Service。

新建文件：

```text
features/users/actions.ts
```

### 1. 完整代码

```ts
"use server";

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";

import { createUser } from "./service";

import {
  createUserSchema,
  toFieldErrors,
  type CreateUserState,
} from "./schemas";

export async function createUserAction(
  _prevState: CreateUserState,
  formData: FormData
): Promise<CreateUserState> {
  // 读取表单数据
  const values = {
    name: String(formData.get("name") ?? ""),
    email: String(formData.get("email") ?? ""),
    username: String(formData.get("username") ?? ""),
    phone: String(formData.get("phone") ?? ""),
  };

  // 使用 Zod 校验表单数据
  const parsed = createUserSchema.safeParse(
    Object.fromEntries(formData.entries())
  );

  // 校验失败
  if (!parsed.success) {
    return {
      message: "请检查表单内容",
      fieldErrors: toFieldErrors(parsed.error),
      values,
    };
  }

  // 调用 Service 创建用户
  const result = await createUser(parsed.data);

  // 处理用户名或邮箱重复
  if (!result.success) {
    return {
      message: result.message,
      fieldErrors: {
        [result.field]: [result.message],
      },
      values,
    };
  }

  // 刷新用户列表缓存
  revalidatePath("/admin/users");

  // 创建成功后返回用户列表
  redirect("/admin/users?created=1");
}
```

### 2. 理解 safeParse

```ts
const parsed = createUserSchema.safeParse(
  Object.fromEntries(formData.entries())
);
```

这里有两层操作。

第一层：

```ts
Object.fromEntries(formData.entries())
```

将 FormData 转换成普通 JavaScript 对象。

例如：

```ts
{
  name: "张三",
  email: "zhangsan@example.com",
  username: "zhangsan",
  phone: "13800000001",
  password: "12345678"
}
```

第二层：

```ts
createUserSchema.safeParse(...)
```

使用前面定义的 Zod Schema 校验对象。

`safeParse()` 不会因为校验失败直接抛出异常，而是返回一个结果对象。

校验成功：

```ts
{
  success: true,
  data: {}
}
```

校验失败：

```ts
{
  success: false,
  error: {}
}
```

因此可以通过：

```ts
if (!parsed.success) {
  ...
}
```

判断校验是否通过。

### 3. 为什么要返回 values？

```ts
return {
  message: "请检查表单内容",
  fieldErrors: toFieldErrors(parsed.error),
  values,
};
```

当用户填写错误时，我们不希望页面刷新后所有内容都消失。

因此将用户之前填写的姓名、邮箱、用户名和手机号返回给表单组件。

密码不保留，是出于安全考虑。

### 4. 理解 revalidatePath

```ts
revalidatePath("/admin/users");
```

这行代码用于让 Next.js 重新验证指定路径的数据缓存。

用户新增成功后，用户列表的数据已经发生变化。

因此需要刷新 `/admin/users` 对应的页面数据。

### 5. 理解 redirect

```ts
redirect("/admin/users?created=1");
```

创建成功后跳转回用户列表。

这里使用查询参数：

```text
?created=1
```

是为了让列表页面知道用户刚刚完成了新增操作，后面可以据此显示成功提示。

需要注意：Next.js 的 `redirect()` 会通过内部机制终止当前执行并完成跳转，不要把它放在会捕获该跳转异常的 `try/catch` 中。

### 2. 为什么要使用 use client？

```tsx
"use client";
```

本组件使用了 React 的 `useActionState` Hook。

Hook 需要在客户端组件中使用，因此文件顶部需要声明 `"use client"`。

注意，这并不意味着表单的业务逻辑全部在浏览器执行。

真正创建用户的 `createUserAction` 仍然运行在服务端。

### 3. 理解初始状态

```ts
const initialState: CreateUserState = {};
```

这是表单刚打开时的初始状态。

此时没有错误信息，也没有需要回显的字段。

### 4. 理解 useActionState

```ts
const [state, action, pending] = useActionState(
  createUserAction,
  initialState
);
```

这里将 Server Action 和表单状态关联起来。

当用户提交表单：

1. 表单调用 `action`。
2. Next.js 将表单数据发送到服务端。
3. 服务端执行 `createUserAction`。
4. 如果校验失败，Action 返回错误状态。
5. 组件通过 `state` 获取错误信息。
6. 如果正在提交，`pending` 就是 `true`。

因此不需要自己再写一套请求状态管理代码。

### 5. 理解 defaultValue

```tsx
defaultValue={state.values?.name}
```

`defaultValue` 用于设置输入框的初始值。

当服务端返回校验错误时，之前填写的姓名就可以重新显示。

这里使用的是非受控输入框，不需要为每个输入框单独维护 React 状态。

### 6. 理解 aria-invalid 和 aria-describedby

```tsx
aria-invalid={!!nameError}
aria-describedby={nameError ? "name-error" : undefined}
```

`aria-invalid` 用于标记输入框当前是否存在错误。

`aria-describedby` 用于关联错误说明。

例如：

```tsx
<p id="name-error">
  请输入姓名
</p>
```

这样不仅可以显示错误信息，也有利于辅助技术识别输入框和错误说明之间的关系。

type SearchParams = Promise<
  Record<string, string | string[] | undefined>
>;

export async function UserList({
  searchParams,
}: {
  searchParams: SearchParams;
}) {

                  })}
                </TableCell>
              </TableRow>
            ))}

            {items.length === 0 && (
              <TableRow>
                <TableCell
                  colSpan={6}

## 十一、本篇总结

本篇完成了用户新增功能，打通了从前端表单到数据库写入的完整流程。

回顾一下，本篇主要学习了：

1. HTML 表单与 FormData。
2. Next.js Server Action。
3. React 19 的 useActionState。
4. Zod 数据校验。
5. TypeScript 类型推导。
6. Argon2 密码哈希。
7. Prisma 嵌套写入。
8. 数据库唯一约束异常处理。
9. Next.js 页面跳转与缓存刷新。

尤其要理解的是，用户新增并不只是执行一条数据库 INSERT 语句。

一个真正可用的用户创建功能，需要同时考虑：

- 输入数据是否合法。
- 用户名和邮箱是否重复。
- 初始密码如何安全保存。
- 用户资料与登录凭据如何关联。
- 创建失败时如何反馈。
- 创建成功后如何刷新页面。

我们现在建立的结构是：

```text
features/users/
├── components/
│   ├── user-list.tsx
│   └── user-create-form.tsx
├── actions.ts
├── schemas.ts
└── service.ts
```

后续实现用户编辑、密码重置、用户停用等功能时，都可以沿用这一套结构。

**安全提醒：** 本篇先完成业务功能，stepby 当前阶段还没有接入 Better Auth 和权限控制。因此，新增用户的页面和 Server Action 暂时没有身份认证及权限校验，不应将当前后台作为可公开访问的正式管理系统。后续接入 Better Auth 后，需要在页面和服务端操作入口补充身份及权限验证，同时配置与当前 Argon2 哈希方案兼容的密码验证方式。

下一篇可以继续实现用户资料编辑，让用户管理从查询、新增逐步扩展到完整的 CRUD 操作。
